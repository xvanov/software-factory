1"""Vacuity classifier — is an acceptance criterion satisfiable by a no-op? 

2 

3Named after Beer et al. 2001 ("vacuity" in formal verification: a property 

4that passes not because the implementation is correct, but because the 

5property is too weak to fail on anything). The motivating incident (see 

6``apps/factory/directions/019-exteroception-v1-close-the-sensing-gap/``): the 

7password-reset feature was certified by three green tests against criteria 

8that only asserted a status code and an absence — 

9 

10 - "returns 202" 

11 - "the token is not in the response body" 

12 - "no error is raised" 

13 

14— none of which requires an email to ever be sent. A fixed-response HTTP 

15handler with no transport layer at all satisfies every one of them. That 

16feature shipped with no working reset path four times before anyone noticed, 

17because nothing in the acceptance criteria forced an artifact (the reset 

18email) to actually arrive. 

19 

20This module is a deterministic, LLM-free classifier (Flow A, 

21``apps/factory/directions/019-exteroception-v1-close-the-sensing-gap/flow.md``) 

22run at direction triage, before any persona is invoked. It sorts each parsed 

23acceptance-criterion string into exactly one of two buckets: 

24 

25``positive-observable`` 

26 Names an outcome a client could observe at the system boundary — response 

27 *content* ("returns the created goal with status 'active'", "the body 

28 contains the token"), an artifact arriving ("an email arrives containing 

29 a link", "a file downloads"), or a visible state change ("appears in the 

30 list", "the page shows the toast", "redirects to /dashboard", "persists 

31 across reload", "a subsequent GET returns it"). 

32 

33``vacuous-satisfiable`` 

34 A fixed-response or reject-everything no-op could satisfy it with zero 

35 real implementation behind it. Several shapes, each independently 

36 sufficient: 

37 

38 1. **Bare status-code / success assertion** — "returns 202", "responds 

39 with a 2xx" — but ONLY when nothing else in the criterion names real 

40 content (see "insufficient alone" below); "returns 200 with JSON body 

41 {"status": "ok"}" is NOT this shape, because the JSON payload IS named 

42 content. 

43 2. **Pure absence / negation** — "does not leak the token", "no error is 

44 raised", "without a stack trace" — again only when the residue after 

45 the negation names nothing else (see below); "users can submit proof 

46 ... without needing to paste a YouTube URL" is NOT this shape, because 

47 "submit proof ... " is a positive capability independent of the 

48 negated clause. 

49 3. **Pure non-observable / process fact** — "the code is refactored", 

50 "tests pass", "coverage increases", "a backend test covers X" — 

51 describes an internal/process fact, not anything a client of the 

52 system could observe. 

53 4. **Vague success/correctness language** — "responds correctly", 

54 "returns a valid response", "returns OK", "no exception is thrown", 

55 "completes cleanly", "well-formed", "handled gracefully", "a success 

56 status", "idempotent" — asserts correctness without naming what 

57 correct output actually looks like. A no-op that never errors 

58 trivially "responds correctly" by this wording. 

59 5. **Enforcement/process verbs with no named observable artifact** — 

60 "enforces token validity", "revokes prior active sessions", 

61 "validates X", "restricts Y", "settings are reviewed and hardened". 

62 A reject-everything (or accept-everything) handler can "enforce", 

63 "reject", "revoke", or "restrict" trivially without implementing the 

64 actual policy, AS LONG AS nothing else in the criterion (or the 

65 positive lexicon) names the resulting observable behavior (a 

66 specific status code on the wrong input, a session cookie that stops 

67 working, a field that appears/disappears). This is deliberately 

68 aggressive — see "Design tension" below. 

69 

70Bucket 1 and 2 are "insufficient alone": a bare status code or a negation 

71does not, by itself, prove nothing else in the sentence names real content. 

72Both are checked with a residue analysis — see ``_has_sufficient_residue``. 

73Buckets 3-5 are unconditional once matched (no residue check): the operator 

74review that shaped this module found that giving them the same leniency 

75either let real vacuous claims slip through (F4) or required implausibly 

76long exemption lists. 

77 

78A criterion that mixes a negation with a positive clause ("returns the goal 

79AND does not leak the token") is ``positive-observable``: the positive half 

80already forces real behavior, so the no-op can no longer pass. Likewise a 

81criterion embedding a literal JSON-shaped value (``{"status": "ok"}``) is 

82``positive-observable`` regardless of an accompanying bare status code — a 

83no-op that emits an ARBITRARY fixed body would not, in general, happen to 

84match a specific named field/value. 

85 

86Design tension (read before extending the vacabulary further): Bucket 5 

87(enforcement verbs) is inherently the fuzziest heuristic here — "validates X" 

88legitimately describes real, checkable behavior in many contexts. It is kept 

89aggressive on purpose because the operator review's motivating case (a 

90password-reset direction whose ONLY criteria were "enforces token validity", 

91"revokes prior sessions", and an absence) is exactly the shape a reviewer 

92must catch, and under-flagging is the direction's explicitly accepted safe 

93failure mode (see :func:`assess_direction`). Concretely this means a handful 

94of criteria that ARE reasonably specific ("validates each conforms to the 

95base [class], and exposes list_types()") get individually mislabeled 

96``vacuous-satisfiable`` when they sit in an otherwise well-specified 

97direction; this does not change any WHOLE-DIRECTION verdict as long as at 

98least one sibling criterion is genuinely positive-observable, which is the 

99only thing :func:`assess_direction` acts on. 

100 

101Fail-safe direction: the two buckets are the only two labels this module 

102emits, and the DEFAULT — when nothing here recognizes a criterion as 

103vacuous — is ``positive-observable``. Blocking a real, well-formed criterion 

104because a crude regex didn't understand it would wedge triage on every 

105direction that phrases things unusually; the asymmetry the direction cares 

106about is a no-op sailing through, not a legitimate criterion being flagged. 

107Callers that need "no verdict" semantics (e.g. an internal classifier crash) 

108should catch exceptions around :func:`assess_direction`'s call site, or use 

109its own try/except — see the docstring there. Note also that a direction 

110with NO acceptance criteria at all bypasses this gate entirely (empty 

111acceptance is reported separately, unchanged, as missing 

112``acceptance_criteria`` — see ``factory.backpressure.validator``); this 

113module has nothing to classify and makes no claim either way. 

114"""

132def _clean(text: str) -> str: 

133 t = text 

134 t = re.sub(r"`+", "", t) 

135 t = re.sub(r"\*\*|\*|__|_", "", t) 

136 t = re.sub(r"^\s*\[[ xX]\]\s*", "", t) 

137 t = re.sub(r"\s+", " ", t).strip() 

138 return t.lower()

162# -------------------------------------------------------------------------- 

163# Pattern 2: pure absence / negation. "Insufficient alone" — see 

164# ``_has_sufficient_residue``. 

165# 

166# Deliberately does NOT include "no longer <verb>" ("exec.py invocations no 

167# longer use shell=True", "the detector no longer fires on the same 

168# subject" — Flow D's own built-in criterion, called out there as 

169# "impossible to satisfy with a no-op"). A "no longer" criterion regresses 

170# against a CURRENTLY-TRUE bad state (the vulnerable call, the firing 

171# detector): a no-op that changes nothing leaves that bad state intact and 

172# fails the criterion. That's the opposite of "does not leak the token" or 

173# "no error is raised", which assert an absence in output the system never 

174# had to produce in the first place — a no-op trivially has nothing to leak 

175# and raises nothing. Treating both shapes the same would block every 

176# regression/security-fix finding of this shape on a technicality the 

177# direction's own Flow D disagrees with. 

178# -------------------------------------------------------------------------- 

179 

180_NEGATION_RE = re.compile( 

181 r"\b(?:does\s+not|doesn't|never|no\s+error|is\s+not|isn't|" 

182 r"cannot|can't|without|won't|will\s+not|not\s+leak|not\s+expose|" 

183 r"not\s+return|not\s+raised|not\s+present|not\s+included|not\s+in\b|" 

184 r"requires?\s+no\b|needs?\s+no\b|nothing\s+is)\b", 

185 re.IGNORECASE, 

186)

252# -------------------------------------------------------------------------- 

253# Positive-observable content markers. Deliberately does NOT include bare 

254# words like "ok" or "success" — "returns 200 OK" must not be credited as 

255# positive just because "OK" is in the string (the calibration trap named in 

256# the direction's implementation plan). Also excludes VAGUE adjectives 

257# (expected/correct/valid/proper/appropriate/right/desired) immediately 

258# before a generic noun (response/value/result/output/field) from the 

259# "returns/contains the <noun>" branches (F5) — "returns the expected 

260# response" is not naming content, it is Pattern 4 above. 

261# -------------------------------------------------------------------------- 

262 

263_VAGUE_ADJ = r"(?:expected|correct|valid|proper|appropriate|right|desired)" 

264

266 r"\b(?:" 

267 r"body\s+(?:contains|includes|has)|" 

268 r"response\s+(?:contains|includes)|" 

269 rf"contains?\s+the\s+(?!{_VAGUE_ADJ}\b)|" 

270 rf"includes?\s+the\s+(?!{_VAGUE_ADJ}\b)|" 

271 rf"returns?\s+the\s+(?!\d|{_VAGUE_ADJ}\b)\w+|" 

272 r"returns?\s+it\b|" 

273 r"lists?\b|" 

274 r"appears?\s+in\b|" 

275 r"shows?\s+the|displays?\s+the|" 

276 r"persists?\s+across|" 

277 r"redirects?\s+to|" 

278 r"subsequent\s+get|" 

279 r"email\s+arrives|arrives\s+containing|" 

280 r"downloads?\b|" 

281 r"opens?\s+a\s+working|" 

282 r"page\s+shows|" 

283 r"toast\s+(?:appears|shows)|" 

284 r"is\s+(?:visible|displayed)\s+(?:in|on)" 

285 r")\b", 

286 re.IGNORECASE, 

287)

289# A "positive" verb (returns/contains/includes/shows/...) immediately after a 

290# negation cue is NOT a positive clause — "never returns the reset token" is 

291# an absence assertion, not a claim that content is returned. Without this, 

292# ``_POSITIVE_RE``'s broad "returns the <noun>" branch would credit exactly 

293# the kind of criterion the calibration is meant to catch (see 019's 

294# password-reset incident: "the token is not in the response body"-shaped 

295# text is common in security criteria). Masked out of a scan COPY only, so a 

296# genuinely separate positive clause elsewhere in the same criterion (the AND 

297# rule) still counts. 

298_NEGATION_WORD_RE = ( 

299 r"(?:never|does\s+not|doesn't|cannot|can't|won't|will\s+not|is\s+not|" 

300 r"isn't|no\s+longer|not)" 

301) 

302_POSITIVE_VERB_RE = ( 

303 r"(?:returns?|returning|contains?|containing|includes?|including|shows?|" 

304 r"showing|displays?|displaying|lists?|listing|redirects?|redirecting|" 

305 r"persists?|persisting|appears?|appearing|arrives?|arriving|downloads?|" 

306 r"downloading)" 

307) 

308_NEGATED_POSITIVE_VERB_RE = re.compile( 

309 rf"\b{_NEGATION_WORD_RE}\s+{_POSITIVE_VERB_RE}\b", re.IGNORECASE

313# Residue analysis for Patterns 1 and 2 (F1): a bare status code or a 

314# negation does not, alone, prove the rest of the sentence is content-free. 

315# After stripping the matched trigger phrase(s), tokenize what's left and 

316# count tokens that are NOT (a) true stopwords/prepositions/modals, (b) 

317# generic HTTP/API vocabulary (get/post/returns/response/body/endpoint/...), 

318# or (c) generic security/account vocabulary that shows up on BOTH sides of 

319# the vacuous/positive line in this corpus (token, password, session, 

320# existence, single-use, reset, issues/discloses...) and therefore does not, 

321# by itself, distinguish a real claim from a restatement of the negated 

322# subject. If >=3 such tokens remain, the criterion names something real and 

323# is NOT flagged via bucket 1/2 alone (though bucket 3-5 may still apply). 

324# 

325# This list is deliberately curated against the operator review's concrete 

326# cases, not exhaustive: "the token is not in the response body" (no 

327# residual content -> stays vacuous) vs. "users can submit proof through an 

328# in-app capture or upload path without needing to paste a YouTube URL" (five 

329# non-generic content words survive -> not vacuous via this bucket). 

330# -------------------------------------------------------------------------- 

331

338 "this", "these", "those", "it", "its", "their", "they", "we", "you", 

339 "your", "i", "not", "no", "never", "does", "do", "did", "cannot", 

340 "cant", "wont", "will", "must", "should", "shall", "only", "also", 

341 "both", "from", "into", "onto", "than", "so", "such", "which", "who", 

342 "whom", "whose", "there", "here", "http", "https", "e", "g", "eg", 

343 "can", "could", "may", "might", "would", "through", 

344 # HTTP verbs / generic response vocabulary

370def _content_token_count(text: str) -> int: 

371 """Count tokens in ``text`` that survive the non-content exclusion list.""" 

372 return sum( 

373 1 

374 for tok in _WORD_RE.findall(text) 

375 if len(tok) > 1 and tok not in _NON_CONTENT_WORDS 

376 )

379_RESIDUE_THRESHOLD = 3 

380 

381 

382def _has_sufficient_residue(cleaned: str) -> bool: 

383 """True if, after removing every status-code/success/negation match, 

384 at least ``_RESIDUE_THRESHOLD`` content tokens remain.""" 

385 residue = _STATUS_CODE_RE.sub(" ", cleaned) 

386 residue = _SUCCESS_WORD_RE.sub(" ", residue) 

387 residue = _NEGATION_RE.sub(" ", residue) 

388 return _content_token_count(residue) >= _RESIDUE_THRESHOLD

391@dataclass 

392class CriterionClass: 

393 """The classification of one acceptance criterion.""" 

394 

395 label: CriterionLabel 

396 reasons: list[str] = field(default_factory=list) 

397 

398 

399def classify_criterion(text: str) -> CriterionClass: 

400 """Classify a single acceptance-criterion string. 

401 

402 Deterministic, case-insensitive, resilient to markdown noise. See the 

403 module docstring for the full heuristic, its bucket-by-bucket rationale, 

404 and its Flow A provenance. 

405 """ 

406 cleaned = _clean(text) 

407 

408 # A literal structured value trumps everything else — naming an exact 

409 # payload shape is "content" regardless of an accompanying bare status 

410 # code (F1: sacrifice 078, 101). 

411 if _JSON_LITERAL_RE.search(cleaned): 

412 return CriterionClass( 

413 label="positive-observable", 

414 reasons=["embeds a literal structured value (JSON-shaped content)"], 

415 ) 

416 

417 # Scan copy with negated positive-verbs masked out, so "never returns the 

418 # token" can't satisfy the "returns the <noun>" branch — see 

419 # ``_NEGATED_POSITIVE_VERB_RE``'s docstring above. 

420 positive_scan = _NEGATED_POSITIVE_VERB_RE.sub(" omits ", cleaned) 

421 if _POSITIVE_RE.search(positive_scan): 

422 return CriterionClass( 

423 label="positive-observable", 

424 reasons=["names response content, a delivered artifact, or a visible state change"], 

425 ) 

426 

427 # Unconditional vacuous triggers (buckets 3-5): once matched, no residue 

428 # check — see the module docstring's "Design tension" note. 

429 reasons: list[str] = [] 

430 if _VAGUE_POSITIVE_RE.search(cleaned): 

431 reasons.append("vague success/correctness claim with no named observable output") 

432 if _ENFORCEMENT_RE.search(cleaned): 

433 reasons.append( 

434 "enforcement/process verb with no named observable artifact " 

435 "(a reject-everything or accept-everything no-op can satisfy it)" 

436 ) 

437 if _PROPERTY_CLAIM_RE.search(cleaned): 

438 reasons.append("internal lifecycle property asserted with no stated observable check") 

439 if _NON_OBSERVABLE_RE.search(cleaned): 

440 reasons.append("describes an internal/process fact, not a boundary-observable outcome") 

441 if reasons: 

442 return CriterionClass(label="vacuous-satisfiable", reasons=reasons) 

443 

444 # Buckets 1-2 (F1): insufficient alone. Only flag if the residue left 

445 # after removing the trigger phrase(s) is itself content-free. 

446 status_hit = bool(_STATUS_CODE_RE.search(cleaned) or _SUCCESS_WORD_RE.search(cleaned)) 

447 negation_hit = bool(_NEGATION_RE.search(cleaned)) 

448 if (status_hit or negation_hit) and not _has_sufficient_residue(cleaned): 

449 residue_reasons: list[str] = [] 

450 if status_hit: 

451 residue_reasons.append("bare status-code/success assertion with no named response content") 

452 if negation_hit: 

453 residue_reasons.append("pure absence/negation with no accompanying positive clause") 

454 return CriterionClass(label="vacuous-satisfiable", reasons=residue_reasons) 

455 

456 return CriterionClass( 

457 label="positive-observable", 

458 reasons=["no vacuous pattern matched (default: assume meaningful)"], 

459 )

476

490def suggest_rewrite(criterion: str) -> str: 

491 """Return one deterministic, criterion-aware rewrite suggestion. 

492 

493 Cheap and template-based — not a persona call. Picks a template by which 

494 vacuous pattern matched so the suggestion echoes back something specific 

495 to the criterion (e.g. the status code it named) rather than a single 

496 generic line for everything. 

497 """ 

498 original = criterion.strip() 

499 cleaned = _clean(criterion) 

500 

501 code_match = _STATUS_CODE_RE.search(cleaned) 

502 if code_match: 

503 code = code_match.group(0) 

504 return ( 

505 f'"{original}" is satisfiable by a fixed-response no-op handler. ' 

506 f"Name the response content a client would observe, e.g.: " 

507 f'"returns {code} and the response body contains the created ' 

508 f'<resource> with its <field>; a subsequent GET returns it."' 

509 ) 

510 if _ENFORCEMENT_RE.search(cleaned) or _PROPERTY_CLAIM_RE.search(cleaned): 

511 return ( 

512 f'"{original}" describes an enforcement/lifecycle property with no ' 

513 f"stated observable check — a reject-everything or accept-everything " 

514 f"handler can satisfy it trivially. Rewrite to name the observable " 

515 f'consequence, e.g.: "a request with an invalid/expired value is ' 

516 f'rejected with 401/403, and a request with a valid value succeeds; ' 

517 f'a session cookie issued before revocation stops working afterward."' 

518 ) 

519 if _VAGUE_POSITIVE_RE.search(cleaned): 

520 return ( 

521 f'"{original}" asserts correctness without saying what correct ' 

522 f"output looks like. Rewrite to name the actual response content, " 

523 f'e.g.: "returns 200 and the response body contains {{"id": ' 

524 f'<created-id>, "status": "active"}}."' 

525 ) 

526 if _NEGATION_RE.search(cleaned): 

527 return ( 

528 f'"{original}" only asserts an absence — a handler that does nothing ' 

529 f"also satisfies it. Pair it with a positive outcome, e.g.: " 

530 f'"returns the created <resource> and the response body never ' 

531 f'includes the raw value; a subsequent GET confirms the field is ' 

532 f'absent while the <resource> itself is present."' 

533 ) 

534 if _NON_OBSERVABLE_RE.search(cleaned): 

535 return ( 

536 f'"{original}" describes an implementation/process detail, not ' 

537 f"something observable at the system boundary. Rewrite to name what " 

538 f'a client sees, e.g.: "a subsequent GET /<resource>/{{id}} returns ' 

539 f'the updated <field> value."' 

540 ) 

541 return ( 

542 f'"{original}" does not name an observable outcome. Rewrite to name ' 

543 f'response content, a delivered artifact, or a visible state change, ' 

544 f'e.g.: "the response body contains <field>" or "the page shows ' 

545 f'<state>."' 

546 )

549def assess_direction(criteria: list[str]) -> VacuityAssessment: 

550 """Classify every criterion and decide whether the whole set is vacuous. 

551 

552 ``all_vacuous`` is True only when ``criteria`` is non-empty AND zero 

553 criteria classify ``positive-observable`` — an empty list is "no verdict", 

554 not "vacuous" (the caller already reports empty acceptance separately as 

555 missing ``acceptance_criteria``; a vacuity gate has nothing to say about a 

556 direction with no criteria to classify). 

557 

558 Fail-safe: if :func:`classify_criterion` raises for any reason, the whole 

559 assessment degrades to "no verdict" — ``all_vacuous=False``, every 

560 criterion reported ``positive`` (i.e. not held against the direction), 

561 and ``error`` set to the exception repr. A crashing classifier must never 

562 block a direction; it is a quality gate, not a safety gate, and the 

563 caller should log the ``error`` field as a warning. 

564 """ 

565 if not criteria: 

566 return VacuityAssessment(all_vacuous=False, vacuous=[], positive=[]) 

567 

568 vacuous: list[str] = [] 

569 positive: list[str] = [] 

570 try: 

571 for criterion in criteria: 

572 result = classify_criterion(criterion) 

573 if result.label == "vacuous-satisfiable": 

574 vacuous.append(criterion) 

575 else: 

576 positive.append(criterion) 

577 except Exception as exc: # noqa: BLE001 - fail-safe: a crash must never block 

578 return VacuityAssessment( 

579 all_vacuous=False, 

580 vacuous=[], 

581 positive=list(criteria), 

582 error=repr(exc), 

583 ) 

584 

585 all_vacuous = len(positive) == 0 

586 return VacuityAssessment(all_vacuous=all_vacuous, vacuous=vacuous, positive=positive)
